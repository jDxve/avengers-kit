# File uploads

Scope: users sending files to a NestJS backend from Flutter or React, where the files are stored, and how they are downloaded again. The upload rules live in [`nestjs-standards` 12](../../nestjs-standards/references/12-api-behavior-and-external-dependencies.md) "Uploads" and the [`nestjs-standards` 09](../../nestjs-standards/references/09-security-baseline.md) checklist; `security-engineering` turns them into `SEC-API-09`. This recipe adds the storage flow, signed URLs, and the client side.

## When it is justified

The project's contract states that users upload files, and what kinds. Object storage is the infrastructure `nestjs-standards` [03](../../nestjs-standards/references/03-stack.md) lists for "You accept uploads", so it arrives with that stated need, and the storage provider is an Open decision for Dave (AGENTS.md rule 6; kit rule). Malware scanning and content disarm are also Open decisions: the OWASP File Upload Cheat Sheet recommends them where available, and each is a vendor or a service.

## Contract sections it fills

- Domain: a file record (owner, tenant where the project has one, server-generated storage key, size, the type detected from content, an optional display name, status such as `pending`, `ready`, `rejected`).
- API: request an upload, confirm it, request a download. Error codes for too large, wrong type, and not found.
- Authorization: who may upload to which parent record, and who may download each file.
- Security: the boundary rows below, and where file names and metadata must never appear.
- Invariants, Failure paths, Tests, Release (bucket name and storage credentials by secret name), Open decisions (storage provider, scanning, signed URL lifetimes, allowed types and sizes).

## Invariants and enforcers

| Invariant | Enforced by |
| --- | --- |
| Only the types the contract names are accepted, judged by content (file signature, and decoding where possible), never by the extension or the client's `Content-Type` | [`nestjs-standards` 12](../../nestjs-standards/references/12-api-behavior-and-external-dependencies.md) "Uploads"; `SEC-API-09`. OWASP: list allowed extensions; the `Content-Type` is user-supplied and trivial to spoof; signature checks are not enough on their own |
| The size limit is enforced before any expensive processing, and for archives after decompression | `nestjs-standards` 12; OWASP "Upload and Download Limits". OWASP does not recommend accepting ZIP files |
| The storage key is generated by the server; the client's file name never becomes a path | `nestjs-standards` 12; OWASP "Filename Safety" (a random name such as a UUID) |
| A display name, if kept, is length-limited and restricted to an allowed character set | OWASP "Filename Safety" (maximum length; no leading periods, sequential periods, or leading hyphens) |
| Files live in object storage, never in the app's root or any executable web root | `nestjs-standards` 09 and 12; OWASP "File Storage Location" (a different host first, outside the webroot second) |
| Upload and download go through short-lived signed URLs bound to one server-generated key, with lifetimes the contract states | Kit rule, `docs/contracts/kit-skills.md` section 9. OWASP's equivalent for public access is a handler that maps an id to the file |
| Ownership is checked before a download URL is issued, the same way as any other resource | `SEC-API-01`, `SEC-API-09`; OWASP "User Permissions" |
| An uploaded object is not downloadable until the server has validated it after upload, and a rejected one is deleted | Kit rule: status `pending` until the confirm step validates content, size, and type |
| Images are decoded and re-encoded, with metadata stripped | OWASP "File Content Validation" (it notes re-encoding does not guarantee all malicious content is removed). Stripping also removes location data from photos (kit rule) |
| File contents and sensitive metadata are never logged, and a signed URL is treated as a credential in logs | `nestjs-standards` 12; `SEC-LOG-01`, `SEC-LOG-04` (kit rule for the signed URL) |

## Flutter

The picker, the upload, and its progress live in the data and connected layers; a `ui/` widget gets progress and status as values and a cancel callback (`ui-isolation`). The client's size and type checks are UX only, so the user learns early; the server decides. The "request an upload" call carries an idempotency key per user intent, so a retry after a dropped connection does not create two records ([`flutter-standards` 10](../../flutter-standards/references/10-feature-anatomy-worked-example-auth.md)). Asking for photo or file permissions follows `SEC-MOB-19`.

## React or Next.js

Client-side checks are UX, never enforcement ([`react-standards` 05](../../react-standards/references/05-rules.md) 4.5). The upload goes through the one client in `lib/api/` (4.4). A Next.js route handler that receives a file is a public endpoint with the same rules as any API route (`SEC-WEB-13`). With cookie auth, the upload request is protected against CSRF (`SEC-API-16`; OWASP lists CSRF protection for uploads).

## NestJS

Body size limits are set per route ([`nestjs-standards` 12](../../nestjs-standards/references/12-api-behavior-and-external-dependencies.md) "HTTP"). Request schemas for upload metadata are strict Zod (`SEC-API-03`). The file record follows `database-drizzle`, including tenant scoping (`07-tenant-scoping.md`). Validation that is slow (re-encoding, scanning) runs as a job when `background-jobs.md` applies; the file stays `pending` until it finishes. Calls to the storage provider have timeouts ([`nestjs-standards` 12](../../nestjs-standards/references/12-api-behavior-and-external-dependencies.md) "External integrations").

## Security items

`SEC-API-01`, `SEC-API-02`, `SEC-API-03`, `SEC-API-08`, `SEC-API-09`, `SEC-API-16`, `SEC-LOG-01`, `SEC-LOG-04`, `SEC-WEB-13`, `SEC-MOB-19`.

## Failure paths and what the user sees

| Failure | What the user sees |
| --- | --- |
| File too large or wrong type | A specific message before the upload starts (client check), and the same code from the server if the client check was bypassed |
| Connection drops mid-upload | A retry action; a retry reuses the intent's key |
| Signed URL expired | The client requests a fresh one once, without asking the user |
| Validation after upload fails | The file shows as rejected with the reason in the project's copy, never the scanner's raw output |
| Download of a file the user may not see | The not-found state (404, `SEC-API-01`) |

## Tests

- e2e from `SEC-API-09`: an oversized file; a file whose extension and declared type lie about its content; user B downloading user A's file returns 404.
- e2e: a name with `../`, a null byte, a double extension, or a colon is stored under a generated key and the display name is rejected or cleaned.
- e2e: a `pending` file cannot be downloaded; a rejected file is gone from storage (storage stub or local emulator).
- Unit with a fake clock: a signed URL past its lifetime is refused.
- Unit: re-encoding strips metadata from a test image.
- Flutter and React: the `ui/` widget for each status renders from plain values (`ui-isolation` "Testing").
