# Internationalization

Scope: copy, plurals, gender, dates, numbers, money, and text direction across Flutter and React or Next.js clients, and what the NestJS API sends so clients can localize it. The resource and formatting rules live in [`flutter-standards` 09](../../flutter-standards/references/09-common-layer.md) "Resources" (`strings.dart`), [`flutter-standards` 16](../../flutter-standards/references/16-production-and-release.md) 11.6 "Localization", and [`react-standards` 05](../../react-standards/references/05-rules.md) 4.6 and [11](../../react-standards/references/11-production-readiness.md). This recipe adds message formats, the error-code mapping across stacks, and the tests. Writing the copy itself is `ui-ux-design`.

## When it is justified

Two levels. With one locale, every project already keeps all copy in resources and formats dates and numbers explicitly (`flutter-standards` 09 and 16 11.4 "Localization readiness"; `react-standards` 11 "Nothing depends on a timezone or locale inherited from the browser by accident"). The i18n library and translation files arrive with a second locale: Flutter retires `Strings` "for ARB or `slang` the moment a second locale appears" (09), and React adds an i18n library when "More than one locale is actually planned, not hypothetical" ([`react-standards` 03](../../react-standards/references/03-stack.md)). The project's contract states the locales (AGENTS.md rule 6). Which React library, and any translation service, is an Open decision for Dave.

## Contract sections it fills

- Goal: the locales supported, and whether any is right-to-left.
- API: error codes and their parameters, never display text; how the user's locale and time zone reach the server for server-rendered text (email, push).
- UI contract: every string the `ui/` widgets show arrives from resources or as a parameter (`ui-isolation` rule 4).
- Invariants, Failure paths, Tests: from the sections below.
- Open decisions: libraries, translation workflow, fallback locale.

## Invariants and enforcers

| Invariant | Enforced by |
| --- | --- |
| All user-facing copy is in resources, including error copy; none is hard-coded in a widget or component | `flutter-standards` 09 "Resources"; `ui-isolation` rule 4; review |
| A message is one translatable unit. Sentences are never concatenated from fragments | ICU "Formatting Messages": translators must be able to move the variable parts, so a message is written and translated as a single unit |
| Plurals and gender go through message formats: `plural` and `select`, with `other` always present | ICU: use `plural` for numbers and `select` for fixed keywords; `other` is always needed; translators add `one`, `few`, and the rest as the target language needs. CLDR's categories are `zero`, `one`, `two`, `few`, `many`, `other`. Flutter ARB files use the same `plural` and `select` syntax (Flutter internationalization docs) |
| Complex arguments sit at the outside of a message, with full sentences in each branch, and `select` outside `plural` | ICU "Complex Argument Types", recommendation |
| Dates, numbers, and money are formatted at display time with the user's locale, never by string interpolation | `flutter-standards` 16 11.6 (`intl`, "never interpolation"); Flutter docs (`NumberFormat`, `DateFormat`); `react-standards` 04 `lib/format/` ("Explicit locale and zone") |
| Money travels as minor units with its currency, and is formatted only at the edge | [`nestjs-standards` 05](../../nestjs-standards/references/05-rules.md) 4.4; `react-standards` [16](../../react-standards/references/16-decisions-this-document-deliberately-doe.md) example |
| Time travels as an instant; the display zone comes from the data or the user's setting, never the device or server default | `nestjs-standards` 4.4 "Time"; `react-standards` 11 |
| Right-to-left locales mirror the layout | Flutter: `GlobalWidgetsLocalizations` sets the default text direction (Flutter docs). Layout is written in start and end terms, never left and right (kit rule) |
| Server errors reach the user as localized client copy, looked up by `code`; the server's `message` is never shown | `api-contract` [`04-errors-and-versioning.md`](../../api-contract/references/04-errors-and-versioning.md) "From a code to client copy"; `react-standards` 4.6; `SEC-WEB-20`, `SEC-LOG-08` |
| Text the server renders (email, push) uses the recipient's stored locale | Kit rule; `push-notifications.md` |

## Flutter

Follow the Flutter internationalization docs for `flutter_localizations`, `intl`, `l10n.yaml`, and ARB files, with `app_en.arb` (or the project's base locale) as the template. The `untranslated-messages-file` option writes the messages not yet translated per locale to a file; CI can fail on a non-empty file (Flutter docs for the option; kit rule for the CI step). `errorToMessage` maps codes to copy ([`flutter-standards` 08](../../flutter-standards/references/08-core-layer.md) "AppException"); per-code copy needs the `code` on `AppException` that `api-contract` `03-flutter-clients.md` describes. Every screen has a test at 2.0x text scale (`flutter-standards` 09), and with a second locale, in the longest locale (16 11.6).

## React or Next.js

The message table keyed by `code` and the generic fallback with the `requestId` follow `api-contract` `04-errors-and-versioning.md` and [`react-standards` 05](../../react-standards/references/05-rules.md) 4.6. Formatting helpers live in `lib/format/` with an explicit locale and zone ([`react-standards` 04](../../react-standards/references/04-structure.md)). Whether the chosen library supports ICU `plural` and `select` is checked against its own documentation before it is picked; the kit did not read those docs. Next.js locale routing is out of scope here and belongs with `react-standards` `17-nextjs-app-router.md`.

## NestJS

The API returns `{ code, message, requestId }` and parameters the client needs to fill its copy, never localized display text ([`nestjs-standards` 05](../../nestjs-standards/references/05-rules.md) 4.3 and 4.6; `api-contract`). Adding a code is a contract change, because until clients map it users see the generic copy (`api-contract` `04-errors-and-versioning.md`). Where the server sends text itself, the user's locale is stored on the user, validated against the supported list.

## Security items

`SEC-WEB-20`, `SEC-LOG-08`, `SEC-MOB-12` (server copy is constrained before it reaches the screen).

## Failure paths and what the user sees

| Failure | What the user sees |
| --- | --- |
| Device or browser locale not supported | The fallback locale the contract names |
| A string not yet translated | The fallback locale's string, never a key name; CI reports it before release (kit rule) |
| An error code the client does not know | Generic copy for the failure class plus the `requestId` (`api-contract` `04-errors-and-versioning.md`) |
| Long translations | Wrapped or scrolled text, never clipped or overflowing (2.0x and longest-locale tests) |

## Tests

- Unit: each plural message in a language with more categories than English. The CLDR page's Ukrainian example: `one` for 1 and 21, `few` for 2 to 4 and 22 to 24, `other` for 0 and 5 to 20.
- Unit: every code in each module's closed error list has copy in every locale (`api-contract` `04-errors-and-versioning.md`).
- Unit: a date formatted for a fixed instant, locale, and zone gives the expected string; nothing reads the machine's zone.
- Flutter widget tests: each screen at 2.0x text in the longest locale, and a pseudo-locale run (`flutter-standards` 16 11.6). If a right-to-left locale is supported, each screen once in it as well (kit rule).
- Web: the same screens rendered in the longest locale in a Playwright run (`testing-strategy` `02-playwright-web.md`).
