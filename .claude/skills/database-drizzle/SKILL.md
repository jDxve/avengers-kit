# Database with Drizzle

How a NestJS project designs, changes, and queries its PostgreSQL schema with Drizzle and drizzle-kit. The database rules live in `nestjs-standards` and `devops-engineering`; this skill links them and adds the migration review, tenant scoping, and soft delete, which no standard covers yet. The repo's established convention beats this skill, and you say so when they differ, except Drizzle and Zod, which repo convention never overrides (ADR-012). A repo on another ORM is flagged for migration, and you stop and ask before adding data code to it.

## Rules that never bend

Each rule names its owner. Read the owner for the detail.

- A constraint is the guarantee; an application check is a convenience. Owner: [nestjs 4.4](../nestjs-standards/references/05-rules.md), and [07](../nestjs-standards/references/07-concurrency-and-data-integrity.md) for which mechanism fits which invariant.
- Index foreign keys used in joins or filters, and validate indexes against real plans. Owner: nestjs 4.4 DEFAULT.
- Every list query has `.limit()`. Owner: nestjs 4.4; pagination semantics in [12](../nestjs-standards/references/12-api-behavior-and-external-dependencies.md).
- Money is never binary floating point; time is an unambiguous instant. Owner: nestjs 4.4.
- No external call inside a transaction: commit, then dispatch through an outbox. Owner: nestjs 4.4.
- Migrations come from `drizzle-kit generate`, are reviewed and committed, and are applied by the controlled deploy step. `drizzle-kit push` runs only against a local disposable database, and only Dave runs it (next rule). Owners: nestjs 4.4, `devops-engineering` [Database](../devops-engineering/SKILL.md), ADR-012.
- Migrations are forward-only; a change that needs schema and code uses expand, deploy, contract. Owner: `devops-engineering` Database.
- No agent runs `drizzle-kit push`, `migrate`, `pull`, `studio`, `psql`, a seed, or any other command against a database, even a local or disposable one. The agent writes the command and the expected result, and Dave runs it. Owners: Dave's decision of 2026-11-08 and AGENTS.md rule 10; the `.claude/settings.json` deny list blocks the named commands, and review catches the rest.
- One exception: an agent may run the NestJS e2e suite, which applies the migrations, only when the suite creates its database for that run and throws it away afterwards (`testing-strategy` `04-nestjs-e2e-and-db.md`, "Who may run the suite"). Owner: Dave's decision of 2026-11-08.
- An agent may write the body of a new migration created with `drizzle-kit generate --custom`, for SQL drizzle-kit cannot generate. It never edits a committed migration; a correction is a new migration, and Dave runs it. Owner: Dave's decision of 2026-11-08; detail in `04-migrations.md`.

## Rules this skill adds

Kit rules, from this skill's contract (`docs/contracts/kit-skills.md` section 4).

- Every tenant-owned table has a non-null tenant column, and every query on it filters by the caller's tenant through one helper. A query without the helper is a review finding, and the finding comes with a cross-tenant test. Detail: `07-tenant-scoping.md`.
- Unique constraints on tenant-owned tables include the tenant column.
- Soft delete only when a contract states the need (restore, audit, legal hold). Then every query and every unique index excludes deleted rows. Detail: `06-soft-delete.md`.

## Migration review checklist

Run on every diff under `drizzle/` or a `schema/` folder. Background for each item is in `04-migrations.md`.

- [ ] DB-MIG-01 The migration was generated by `drizzle-kit generate` from the schema in the same diff, and SQL that drizzle-kit cannot generate is in its own `--custom` migration. Verify: on the branch, `npx drizzle-kit generate` creates no new migration folder (if it does, the diff is incomplete: report it and remove that folder), and `npx drizzle-kit check` passes.
- [ ] DB-MIG-02 Every statement is listed with the lock it takes, and any `ACCESS EXCLUSIVE` lock on a table with rows is called out. Verify: read `migration.sql` against the lock notes in `04-migrations.md` and the PostgreSQL `ALTER TABLE` page; the PR description holds the list.
- [ ] DB-MIG-03 `NOT NULL` on a column of a table with rows is added in steps: nullable column, backfill, then the constraint. Verify: no `ADD COLUMN ... NOT NULL` without a constant default, and no `SET NOT NULL` in the same migration as the column it constrains.
- [ ] DB-MIG-04 An index on a large or busy table is built with `CONCURRENTLY`, alone, outside a transaction block. Verify: read the SQL; after Dave applies it to the local disposable database, `\d <table>` shows no `INVALID` index.
- [ ] DB-MIG-05 A data backfill is separate from the schema change and runs in batches. Verify: no `UPDATE` or `INSERT ... SELECT` on a table in the same migration as DDL on that table.
- [ ] DB-MIG-06 Nothing the deployed code still reads is dropped or renamed. Verify: `git grep -n <column> <deployed tag> -- src` returns nothing for each dropped or renamed column, and every drizzle-kit rename prompt was answered on purpose (`05-expand-and-contract.md`).
- [ ] DB-MIG-07 The PR says whether the migration is reversible, and a destructive one names the backup step Dave runs first. Verify: the line is in the PR or the contract's Release section (`devops-engineering` Database).
- [ ] DB-MIG-08 The committed migrations build the schema from zero. Verify: the e2e suite passes on a database created for that run, migrated from zero, and thrown away afterwards, set up as in `testing-strategy` `04-nestjs-e2e-and-db.md`. An agent runs the suite only when the suite itself creates and drops that database; otherwise it reports the command and Dave runs it.
- [ ] DB-MIG-09 A new tenant-owned table has a non-null tenant column, a foreign key to the tenant, the tenant column in its unique constraints, and the tenant column first in its list indexes. Verify: read the table in `schema/` against `07-tenant-scoping.md`.
